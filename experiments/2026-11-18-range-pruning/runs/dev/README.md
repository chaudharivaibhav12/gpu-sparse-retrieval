# dev (development, not results)

- **Census.** `code/range_bound_census.cpp` on cuda5, on the 500 calibration queries at range sizes 1024, 512 and 256 (k=10; seeds 1/4/16/64/256 and the oracle threshold). It computes work only, with no timing. For every query and size, all reference top-10 documents lie in kept ranges. The README table summarises it. The seed count of 64 was fixed from it.
- **Fixtures.** `tests/check_range_prune.py` passed on the first build of `src/cuda_range_prune.cu` (864 scorer runs, 17,472 answer checks, 12,960 schedule checks, 11 rejections). It was rerun after the coverage counter was tightened to count a range kept by bound == theta only when theta > 0 (14,825 such ranges).
- **Probe.** Full collection, range size 256, 64 seeds, VERIFY=1, 1 round. All 500 answers match the host reference. The scorer's schedule (theta, scored ranges, scored postings) equals the host recomputation and the census on every query. The median query scored 6.3% of the 34,539 ranges. Latencies from this probe were not used: it ran with VERIFY=1 and did not wait for a quiet GPU.

- **Dry run `dev-prune-01`** (`code/run.sh`, DEV=1, 1 process, 1 warm-up + 2 rounds, CPU_LIMIT 1.0). Build and input hashes passed, including the new W512/W256 indexes. Both fixture suites passed, as did both deliberate gate rejections. All nine correctness runs equal the CPU reference, and all three VERIFY=1 seeds-64 runs also match the host schedule. After the first timing process it waited more than 15 minutes for other CPU use to fall below 1.0 core: another user's single-threaded job kept it at 1.1-2.7 cores, with no GPU process. The author stopped it. The CPU limit became 4.0 cores (see `cpu_limit_rationale` in the protocol). Its one timing process was not read.
- **Dry run `dev-prune-02`** (DEV=1, FIXTURES=0, 1 process, 1 warm-up + 2 rounds, CPU_LIMIT 4.0). Passed end to end: both gate rejections; nine correctness runs equal to the reference, three of them VERIFY=1 with matching schedules; nine timing processes with answers equal to the reference; the analysis (11 contrasts, schedules identical across rounds); and the manifest. Its latencies were not read before registration.
- **Dry run `dev-prune-03`**, after recorded run `20261117-cuda5-prune-01` failed when its first replacement could not start: the expectation of the ineligible attempt was left in place, and `expect.py` refused to overwrite it. Fixed in `55a0dde`, which keeps that expectation with the held attempt. DEV=1, FIXTURES=0, CORRECTNESS=0, FORCE_REPLACE=1, 1 process, 1 warm-up + 2 rounds. The forced-ineligible first process was held under `raw/ineligible/` with its expectation, the replacement ran and was accepted, and the run completed through analysis and manifest. Latencies not read.

Outputs stay on cuda5 scratch and are not published.
- **Gate amendment test** (after recorded run `20261117-cuda5-prune-02` failed). A stand-in GPU process (64 MB, `cudaMalloc` + sleep) ran alongside the real v2 scorer on the full collection. A: during index loading only. Whole-life foreign samples 34, released-phase 0, eligible. B: started after the release. Released-phase foreign samples 9, ineligible. The scorer's own process was sampled in all 17 released-phase samples of each. Latencies not read.
- **Robustness test `dev-robust-01`** (amendment 2 script `6313b60`; DEV=1, QUIET=0, 1 process, 0 warm-up + 1 round, `REUSE_FROM` prune-02). The reuse checks passed (prune-02's fixtures and correctness, src/ and tests/ unchanged, copied binary hashes equal to its record), and build, fixtures and correctness were skipped. Timing began about 3 minutes after launch. The run was killed after its second checked timing process and resumed with RESUME=1. The two checked processes were kept, the interrupted one moved to `raw/interrupted/` and repeated, and all nine, the analysis (11 contrasts) and the manifest completed. Latencies not read.
